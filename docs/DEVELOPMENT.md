# 개발 순서와 완료 기준

현재 10/17까지 완료했다. 046의18분류·120경기8,108행동진단과045독립대조가통과했다. 2/3seed에서추가상태정확도개선과기본상태저하가동시에나타났다. 다음10/18은047 기본/추가48/16샘플quota 비교다. 근거는 [10/17 결과](daily/2026-10-17.md)와 [후속 계획](PLAN_AFTER_2026-10-02.md)이다.

각 단계는 작은 실행 가능한 결과를 만든다. 단계 완료 시 실제 명령·결과를 기록하고 다음 단계로 진행한다. 현재는 아래 부분 규격에서 단계 0–3의 로컬 경로를 구현했다. 최신 패치 재현, 로컬 감독 실행(단계 4), 성능 검증(단계 5)은 완료하지 않았다. 이 문단은 초기 구현 이력이다. 최신 상태는 `daily/` 결과와 `LOCAL_EXECUTION.md`를 우선하며 기존 증거는 `VERIFICATION.md`에 보존한다.

초기 단계 0의 기준은 패치 번호가 불명인 원본 파일의 SHA와 `archival-subset-v1` 규격이었다. 9/16의 v2는 기존 4종에 일반 골렘과 소환 전용 토큰을 추가했다. 9/17 최종 v4는 용혈족 부관·공허방랑자를 더한 상점 7종이다. 중간 v3의 잘못된 토큰 상점 등록과 중복 카드 집계는 교정했다. 라이브 패치 일치와 골렘 황금·트리플은 지원하지 않는다. 범위와 차이는 `RULES.md`에 명시했다.

## 단계 0 — 범위와 실행 계약

작성할 결과:

- 기준 패치와 최초 카드 목록, 지원 규칙, 의도적인 단순화 목록
- 엔진 언어와 프로세스 구조에 대한 짧은 설계 결정: 테스트 편의·운영 환경·초기 속도를 근거로 선택
- 관측·액션·카드 ID·종료 이유·seed 규격
- 로컬 개발 checkout과 WSL 고정 실행본을 구분한 환경 기록
- 최소 의존성 목록과 고정 방법

통과 기준: 최소 카드로 reset → 합법 행동 → 전투 → 종료를 실행할 범위가 명확하고, 미구현 효과가 학습 풀에 들어갈 경로가 없다. 실행 장비 미확정 상태에서는 개발과 가벼운 로컬 테스트만 진행한다.

## 단계 1 — 정확한 최소 엔진

능력치 중심 카드와 기본 경제부터 구현한다. 추가 키워드는 해당 이벤트 테스트가 준비된 뒤 도입한다. 무거운 이벤트 프레임워크를 먼저 만들지 않는다.

필수 회귀 사례:

1. `[A,B,C]`에서 A가 공격 후 죽으면 B가 다음 공격자다. 앞선 슬롯의 방어 중 사망도 검증한다.
2. 손패 상한 근처에서 트리플·추가 보상을 받아도 관측 누락과 액션 영역 충돌이 없다. 넘친 보상의 처리 규칙을 명시한다.
3. 모든 합법 액션의 인코딩→디코딩→실행이 일치한다. 잘못된 액션은 정의된 오류로 처리한다.
4. 특정 티어 발견은 그 티어에서만 뽑는다. 발견 선택을 아직 구현하지 않았다면 트리플 지원 범위를 명시적으로 제한한다.
5. 선언한 마지막 턴에 정확히 종료한다. 사망·시간 제한·정상 완료를 구분한다.
6. 같은 seed와 같은 액션열이 같은 결과를 만든다. 다른 세션의 reset·step이 영향을 주지 않는다.
7. 지원하는 효과마다 카드별 결과와 충돌 순서를 검증한다. 도입 전 미지원 효과 카드는 제외한다.

통과 기준: 위 사례와 관측 공간·마스크 불변 조건 테스트 통과. 학습 라이브러리 없이 게임을 완주할 수 있다.

## 단계 2 — 고정 평가와 기준 정책

- 합법 액션 무작위 정책과 단순 구매·레벨업 규칙 정책을 구현한다.
- 버전이 고정된 상대 보드·seed 세트를 준비한다. 학습용과 평가용을 분리한다.
- 승·무·패, 피해, 생존, 턴 수, 강제 종료, 리롤·스왑 횟수를 기계가 읽을 수 있는 형식으로 저장한다.
- 결과와 함께 코드·데이터·평가 규격 해시를 남긴다.

통과 기준: 동일한 정책의 동일 조건 평가를 반복했을 때 결과가 재현된다. 반복 평가가 상대나 다음 평가를 변경하지 않는다.

## 단계 3 — 최소 PPO 학습 연결

- 위치가 유지되는 관측과 합법 액션 마스크로 PPO를 연결한다. 기존 V3 구조는 검토 대상이지 필수 구조가 아니다.
- 먼저 전투 결과 중심의 기준 보상을 사용한다. 트리플·함성 보너스는 별도 비교 실험으로만 추가한다.
- 모델·설정·카드 매핑 저장과 호환성 검사를 구현한다.
- 수치 이상, 잘못된 관측, 마스크 오류는 명확하게 실패시킨다.

통과 기준: 짧은 학습, 저장, 새 프로세스 로드, 고정 평가가 모두 성공한다. 정책이 우수하다는 주장은 아직 하지 않는다.

## 단계 4 — 로컬 WSL 학습 운영

- `docs/LOCAL_EXECUTION.md`에 따라 전용 가상환경과 짧은 성능 측정을 검증한다.
- 실행 명세의 자원·시간·출력·재개 조건을 확정한다.
- 고정 코드 실행본을 준비하고 학습을 실행한다. 작업 하나에 고유 run_id를 사용한다.
- 중단·재개, 중복 실행 방지, checkpoint 보존, 결과 회수를 실제 시험한다.

통과 기준: 로컬 WSL 감독기가 정해진 명세를 실행하고 결과·종료·자원 근거를 보존한다. 절전·재부팅 이후 무중단 생존을 가정하지 않는다.

## 단계 5 — 성능 검증과 확대

- 고정 평가에서 기준 정책과 비교한다. 여러 학습 seed, 충분한 평가 게임 수, 불확실성 구간을 사용한다.
- 평가 횟수와 성능 통과 기준은 실행 전에 실험 명세에 수치로 기록한다.
- 주요 변경을 하나씩 비교하고 보상 증가와 승률 향상을 구분한다.
- 카드 효과 범위를 먼저 확장한다. 처리량 병목을 측정한 뒤 병렬 학습과 엔진 최적화를 검토한다.
- 8인 대전·공유 카드 풀·순위 목표는 별도 확장 단계로 설계한다.

통과 기준: 고정 평가에서 사전에 정한 기준을 충족하고, 성능이 보상 악용이나 평가 데이터 유입 때문이 아니라는 근거를 남긴다.

## 기존 프로젝트에서 확인한 위험

새 구현은 다음 문제를 반복하지 않아야 한다.

- 현재 보드 저장 직후 같은 풀에서 상대 추첨
- 사망자 삭제 뒤 공격 인덱스 미보정
- 손패 11번째 카드의 PLAY와 SWAP 액션 충돌
- 모든 함성·죽메를 공통 버프로 대체
- 승리 보상보다 과도한 트리플 보상
- 카드 필터 변경 후 임베딩 ID 재배정
- Python seed가 C# 엔진까지 전달되지 않음
- 평가가 서버 실행 이력에 의존함
- 실패를 출력만 하고 정상 종료하는 테스트
