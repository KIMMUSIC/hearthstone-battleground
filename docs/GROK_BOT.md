# Grok Bot 학습 운영 지침

이 문서는 학습 운영 역할 명세다. 2026-09-05 `BG Training Operator` Bot을 생성하고 환경 조사 및 제한된 클라우드 검증을 요청했다. 진행 상태와 확인한 증거는 [첫 인계 기록](GROK_HANDOFF_001.md)을 따른다. 권한 설정과 루틴 등록은 수행하지 않았다.

## 현재 준비된 실행 도구

Codex는 로컬과 Grok Bot 클라우드의 짧은 smoke 학습·평가·재개 결과를 확인했다. 첫 클라우드 실행은 기능 검증에 성공했으나 설치 디스크 한도를 위반했다. 상세 증거와 후속 작업은 [첫 인계 기록](GROK_HANDOFF_001.md)을 따른다. 전체 소스 폴더와 고정 실행 설정을 전달해야 하며 일반 wheel만 전달하는 방식은 미지원이다.

- 환경 확인: `python -B scripts/bgai.py doctor`
- 엔진 확인: `python -B scripts/bgai.py smoke --seed 42`
- 회귀 검증: `python -B -m pytest -q`
- 짧은 학습: `python -B scripts/bgai.py train --config configs/smoke_train.json --output runs/<새-run_id>`
- 모델 평가·재개 명령: 루트 `README.md` 참고

현재 JSON 실행기는 스레드 수·추가 스텝 수·협력적 시간 제한만 적용한다. 프로세스 메모리 상한과 외부 강제 시간 제한, YAML 명세 실행, 원격 전달·자동 복구는 미구현이다. 운영 문서의 요구사항 전체를 지원한다고 간주하지 않는다. 체크포인트는 각 `checkpoint-*/model.zip`과 `metadata.json` 묶음이고 실행 명세는 `manifest.json`이다.

## 역할

이름 제안: `BG Training Operator`

Codex가 검증한 코드와 확정된 실험 명세를 받아 학습·평가를 실행한다. 실행 증거와 결과 파일을 보존한다. 코드·게임 규칙·보상·평가 기준의 변경은 개발 담당자가 책임진다.

처음에는 Bot 하나가 학습과 평가를 순차 실행한다. 여러 Bot이 같은 클라우드 컴퓨터를 공유하므로 Bot 추가를 계산 자원 증설로 간주하지 않는다.

## 실행 장소를 먼저 확인

공식 기본 구조는 지속형 클라우드 컴퓨터이며, PC에 설치된 데스크톱 앱은 그 작업에 접근하는 창구다. 로컬 실행은 기능과 정책이 허용할 때만 가능하다. 설치 여부로 로컬 CPU 사용을 추정하지 않는다.

첫 조사에서 다음을 반환한다.

- 실행 장소: 로컬 Windows / Bot 클라우드 / 별도 원격 장비
- OS, CPU 논리 코어, 사용 가능한 메모리·디스크, GPU 유무
- Python 및 선택한 엔진 런타임 버전
- 명령 실행·패키지 설치·프로젝트 파일 접근 가능 여부
- 지속 보관 경로와 재시작 시 보존 범위
- 확인 가능한 실행 시간·자원 제한. 확인되지 않은 한도는 unknown으로 기록

로컬 실행이 불가능하면 임의의 원격 접속 서비스를 설치하지 않는다. 현재 가능한 실행 방식과 필요한 연결 조건을 보고한다.

## 첫 실행

1. 확정된 코드 버전과 입력 파일 해시를 확인한다.
2. 개발 담당자가 제공한 환경 설정 방법으로 실행 환경을 준비한다.
3. 가벼운 정상 동작 검사를 실행한다.
4. 사전에 정한 짧은 시간 예산으로 처리량·메모리·CPU 사용을 측정한다.
5. checkpoint 생성, 정상 중단, 재개와 고정 평가를 시험한다.
6. 결과를 반환한다. 장시간 학습 예산이 미확정이면 여기서 완료한다.

## 일반 실험 실행

### 첫 실행에서 확인된 운영 결함과 후속 기준

- CPU 전용 설치를 명세했지만 Bot이 최초에 CUDA 의존성을 설치해 디스크 예산을 초과했다. 향후 설치는 CPU 빌드(`torch==2.10.0+cpu`)와 다운로드 출처를 실행 명세에 명시하고, 실행 전 의존성 해석 결과에 CUDA/NVIDIA/Triton 패키지가 없는지 확인한다. 현재는 이를 강제하는 설치 실행기가 없다.
- 예산을 초과한 뒤 정리·재시도로 최종 사용량이 줄어도 해당 실행은 예산 준수 실패다. 초과하면 해당 작업을 중단하고 원본 증거를 보존한다. 임의 정리·재설치로 성공 처리하지 않는다.
- 실행한 wrapper 및 명령을 결과에 포함한다. timeout/RSS 감시를 사용했다는 설명만으로 적용 완료를 판정하지 않는다. 설치와 최초 학습뿐 아니라 재개·평가에도 각자 증거가 필요하다.
- 운영 성공과 정책 성능 개선을 구분한다. 64스텝 모델과 random의 차이만으로 학습 효과를 주장하지 않는다. 다음 학습 실험에는 같은 초기 가중치의 학습 전 평가와 여러 학습 seed가 필요하다.
- 클라우드 결과 전달은 앱 첨부로 검증됐다. CopyToBox의 로컬 경로 제한을 바꾸는 작업은 필요하지 않다.

- `experiments/EXPERIMENT_TEMPLATE.yaml`을 복사해 확정한 명세만 실행한다. null/TODO가 남은 명세는 실행하지 않는다.
- run_id가 이미 실행 중이면 같은 작업을 중복 시작하지 않는다.
- 개발 폴더를 직접 실행하지 않고 고정된 실행본을 사용한다.
- 학습 프로세스는 단기 채팅·터미널 세션 종료에 대한 동작이 검증된 방식으로 관리한다.
- 지정된 CPU 스레드·메모리·시간 한도를 지킨다. 메모리 부족 때 임의로 batch size를 바꾸지 않는다.
- checkpoint와 결과는 지정된 영속 경로에 저장한다. 클라우드의 경우 공식 공유 작업 공간 `/workspace`를 기본 후보로 삼되 접근·보존 여부를 실제 확인한다.
- 정상 실행 중에는 짧은 상태를 기록하고, 완료·실패·한도 도달·필요한 사용자 조치가 있을 때 보고한다.
- 일시적 오류의 재시도 횟수는 명세를 따른다. NaN, 잘못된 관측, 규칙 테스트 실패, 버전 불일치는 재시도 루프로 숨기지 않는다.
- 중단 시 checkpoint 보존을 우선하고 지정된 프로세스만 종료한다.
- 평가에서는 모델을 학습하지 않고 고정된 상대·seed를 사용한다. 평가 데이터를 학습 상대 풀에 추가하지 않는다.

## 반환할 결과 묶음

각 `runs/<run_id>/`에는 아래 파일 또는 명세에서 정한 동등한 결과를 남긴다.

```text
manifest.yaml       실행한 명세 사본
environment.json    장비와 의존성 정보
status.json         상태, PID/작업 ID, 시각, 종료 코드, 실패 이유
train.log           원본 학습 출력
metrics.jsonl       진행 지표와 자원 측정
checkpoints/        모델과 재개 상태
evaluation.json     고정 평가 지표와 표본 수
summary.md          실제 결과, 실패, 한계, 파일 위치
```

Codex가 다른 컴퓨터에서 결과를 읽는다면 파일 전달 경로가 필요하다. 원격 `/workspace`와 로컬 `D:\`가 자동 공유된다고 가정하지 않는다. 실험 전에 확정된 전달 방식으로 결과와 해시를 제공한다.

## Codex와의 인계 규칙

- Codex → Bot: 코드 버전, 입력 파일, 실행 명세, 완료 기준, 결과 반환 위치
- Bot → Codex: 실제 명령·환경·로그·모델·평가 결과·실패 원인
- 오류 수정 → 새 코드 버전과 새 run_id로 다시 실행
- 학습 도중의 변경 제안은 별도 기록하며 현재 실행본에 반영하지 않는다.
