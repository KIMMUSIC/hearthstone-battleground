# 상대 구성 다양화 비교 009 — 사전 명세

작성: 2026-09-06. 상태: **설계 고정, 구현·학습 미실행**. 오늘 목표는 비교 계약과 기준선 확인이며 실제 구현은 9/7, 전달 검증은 9/8, 본 학습은 9/9의 범위다.

## 질문과 변경 범위

같은 카드 수·상대 티어·학습량에서 상대의 카드 구성을 다양화하면 제한된 환경의 개발 평가 성능과 행동 안정성이 나아지는가?

현재 기본 상대는 1티어 카드 중 ID가 가장 큰 72387만 반복한다. 카드 수는 턴별 `[1,1,2,2,3,3,4,4]`, 상대 티어는 전부 1이다. 첫 비교에서는 이 크기·티어 일정을 유지하고 1티어 카드 두 종의 구성만 바꾼다. 2티어 카드, 보드 수 증가, 상대 티어 변경은 별도 실험으로 미룬다. 서로 다른 카드의 능력 차이를 포함한 **상대 구성 분포 변경의 효과**이며 난이도를 동일하게 맞춘 실험은 아니다.

학습 상대의 출처는 `data/cards.json`의 지원 카드와 이 문서의 합성 분포다. `configs/eval_opponents.json` 및 과거 평가 산출물을 학습 상대 생성에 읽거나 복사하지 않는다. 작은 카드 풀에서는 생성된 개별 보드가 평가 보드와 우연히 같을 수 있다. 파일·seed 분리와 모든 보드의 완전한 비중복을 혼동하지 않는다.

## 9/7 구현 계약

- `training._config`에 문자열 `opponent_mode`를 추가하고 `fixed-v1`/`diverse-v1`만 허용한다. 생략하면 기존 동작을 유지하는 `fixed-v1`이다. 현재 모든 값에 정수 검사를 적용하므로 이 필드는 명시적으로 분리 검증한다.
- `train` → `BgEnv` → `Game`에 같은 설정을 전달하고 manifest·checkpoint config에 기록한다. 분포 규격 버전과 카드 후보·턴 일정도 실행 manifest에 기록한다.
- `Game.reset(seed)`에서 `random.Random(f'opponent:{seed}')`를 사용해 8턴 상대 일정을 한 번 생성한다. `_shop_rng`·`_combat_rng`를 소비하거나 전역 RNG를 사용하지 않는다. 일정은 에피소드 동안 불변이며 턴 t는 인덱스 `(t-1)%8`을 사용한다. 이번 실험 horizon은 8이다.
- fixed-v1은 기존 상대 일정을 유지한다. 초기화·reset·상대 생성이 상점 추첨 순서나 플레이어 entity ID를 바꾸지 않도록 한다.
- 명시적 `opponents` 입력은 기존 고정 평가 경로로 유지한다. `opponents`와 diverse-v1을 동시에 지정하면 오류로 거부한다. 평가가 학습 분포를 암묵적으로 사용하는 경로를 만들지 않는다.
- 사전에 필요한 두 ID의 존재·1티어·지원 효과를 검사한다. 데이터 변경 후 몰래 다른 카드로 대체하지 않는다. 잘못된 모드와 빈/잘못된 상대 입력도 명확하게 실패한다.
- 상대 미래 보드를 관측에 추가하지 않는다. 현재 37행동·관측 크기·보상·8턴/24행동·플레이어 경제 규칙을 유지한다. 감사용 trace에 실현된 상대 구성과 모드를 기록할 수 있으나 정책 입력과 분리한다.
- 소스 변경에 따른 새 호환성 서명을 사용한다. 구형 metadata를 고쳐 로드하지 않는다. 같은 새 소스로 학습한 두 모드는 동일 고정 평가 환경에서 평가할 수 있어야 한다. 재개는 해당 학습 모드가 다르면 거부한다. 평가 모드 전환 허용과 학습 재개 모드 일치는 별도 조건이다.

### 필수 검증

1. fixed-v1의 고정 seed·행동열이 변경 전 게임 결과와 일치한다.
2. diverse-v1의 동일 seed 재현, 세션 교차 reset/step 간 독립성을 확인한다.
3. 상대 생성 직전·직후 shop/combat RNG 상태 불변을 확인한다. 전투 결과로 이후 궤적이 달라지는 것은 별도로 구분한다.
4. 후보 ID·티어·턴별 크기·보드 순서·모드 오류 처리와 평가 입력 충돌을 검사한다.
5. 평가 파일 읽기 함수를 실패시키는 테스트에서도 학습 상대 생성이 작동하며, 평가 입력 내용·해시는 변하지 않는다.
6. 설정이 실제 환경에 전달되고 manifest와 checkpoint에 보존됨을 검사한다. 호환되지 않는 재개·구형 모델 로드를 거부한다.
7. 관측 공간·마스크·기존 전투/경제 회귀를 검사한다. 검증 전 대규모 학습으로 진행하지 않는다.

## 학습 명세

- 캠페인 식별자: `opponent-diversity-009`. 실제 출력 디렉터리가 이미 존재하면 삭제하지 않고 상태를 확인한 뒤 새 revision ID를 사용한다.
- 조건별 seed: 7,17,27. 순서: fixed7 → diverse7 → fixed17 → diverse17 → fixed27 → diverse27.
- 신규 학습 6회, 각 8,192스텝, 총 49,152스텝. 재개하지 않는다.
- `n_steps=32`, `batch_size=32`, `n_epochs=4`, `checkpoint_interval=8192`, `threads=1`, `max_turns=8`, `max_actions=24`, 학습 함수 협력적 `max_seconds=60`을 공통으로 유지한다.
- seed마다 두 조건의 초기 가중치가 동일함을 파라미터 수준에서 확인한다. ZIP 바이트 해시는 컨테이너 메타데이터 차이로 같지 않을 수 있으므로 그것만으로 초기화 불일치를 판단하지 않는다.
- 최종 기대 timestep 8,192, optimizer update 1,024. 마지막 callback 파일이 아니라 실제 최종 저장 파일을 상태/메타데이터로 선택한다.

## 개발 평가와 사전 판정

과거에 사용한 기본 평가 seeds 101–105, 진단 201–220, holdout008의 301–320은 모두 **결과를 본 개발용**이다. 과거 holdout 기록을 변경하지 않으며 앞으로 최종 미사용 평가라고 부르지 않는다.

009는 구성 분포 실험의 개발 평가다. 새 환경 seed 401–420을 예약하고, reference와 shifted 두 고정 상대 조건은 holdout008의 파일을 그대로 사용한다. 새 seed만으로 완전히 새로운 과제라고 주장하지 않는다. 이후 카드 확장 후의 최종 평가는 별도 명세에서 고정한다.

- 두 상대 파일: `handoff/holdout-008/reference-opponents.json`, `handoff/holdout-008/shifted-opponents.json`. 해시는 [입력 목록](../docs/daily/2026-09-06-inventory.json)에 고정한다.
- 각 조건·seed의 초기/최종 모델 12개 × 상대 조건 2개 × 선택 방식 4개(argmax, stochastic policy seeds 11/22/33) × 환경 seed 20개 = **1,920 에피소드**.
- heuristic/random × 상대 조건 2개 × 환경 seed 20개 = **80 에피소드**. 전체 **2,000 에피소드**, 모델 96보고서+기준선 4보고서=100보고서(보고서당 20게임).
- 초기 모델이 같아도 이번 명세의 초기 평가를 생략하지 않는다. 비교 감사에서 동일 초기 모델의 두 조건 평가 일치를 확인한다.
- 1차 지표: 각 학습 seed에서 두 상대 조건과 확률적 선택 3개의 평균 에피소드 보상을 동등 가중하고 diverse−fixed 차이를 계산한다.
- 후보 유지 기준: 차이의 3개 seed 평균 ≥ +0.25, 3개 중 최소 2개 seed에서 차이 > 0, 전체 확률적 생존율 감소가 5%p 이내. 각 상대 조건의 결과도 별도 공개한다. 이는 운영상 탐색 기준이며 통계적 유의성 기준이 아니다.
- 기준 미충족이면 fixed 유지 또는 원인 진단으로 분기한다. 학습 불안정·심각한 행동 낭비를 숨기지 않는다. 평가 무결성 위반이면 성능 판정을 무효 처리한다.
- 보조 지표: 생존율, 전투 승률, 피해, 동결·턴 종료 비중, 강제 종료, 엔트로피, argmax 성능. 생존은 전체 전장 우승률이 아니다.
- 정책 RNG와 환경 RNG를 구분한다. seed 3개가 독립 학습 반복 단위이며 2,000게임을 독립 학습 반복으로 해석하지 않는다. seed별 차이와 범위를 보고한다.

## 실행 한도와 재개 지점

9/6에는 점검만 하고 학습·평가를 실행하지 않는다. 9/8 smoke와 9/9–10 실험은 그 날 목표에서 수행한다. 9/8 실제 측정 후 단일 진입점·감독기 명세를 고정한다.

현재 출발값은 CPU 1스레드, 샘플링 RSS 2GiB, 작업 단위 180초 이내다. 이는 기존 실험의 운영 범위이며 서비스 보장이나 하드 메모리 상한이 아니다. 전체 2,000평가 trace가 기존 디스크 예산을 넘을 수 있으므로 **상대 조건별 1,000에피소드로 분리**하고 원본+압축본을 포함한 공간을 사전에 산정한다. 기존 결과를 삭제해 공간을 확보하지 않는다. 이용 가능한 공간과 시간에 안 맞으면 학습량·표본 수를 결과를 본 뒤 줄이지 말고 실행 전 명세 revision과 이유를 기록한다.

최종 executable hash, smoke 측정치, cloud 출력 경로, 감독기별 실제 시간·디스크 한도는 **9/8에 채울 실행 게이트**다. 현재 구현되지 않은 소스의 해시를 만들어 넣지 않는다. 이 게이트가 없으면 본 실행을 시작하지 않는다.

반환: 정확한 입력·실행 명세, 원본 stdout/stderr/종료 코드, 초기·최종 모델과 metadata, 평가 원본·summary, 소스·모델 전후 해시, 자원 측정 범위, 실패 원인. Codex가 회수 후 감사하며 실패 원본은 보존한다.
